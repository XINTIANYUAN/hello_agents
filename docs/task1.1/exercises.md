# Task1.1 · 第一章习题解答

以下答案结合第一章的智能体定义、PEAS 和旅行助手案例。第 4 题是扩展设计，第 5 题是仿真方案。文中示例用于说明预期行为，真实运行记录见[学习笔记](learning-notes.md)。[Datawhale 第一章习题原文](https://github.com/datawhalechina/hello-agents/blob/main/docs/chapter1/%E7%AC%AC%E4%B8%80%E7%AB%A0%20%E5%88%9D%E8%AF%86%E6%99%BA%E8%83%BD%E4%BD%93.md#%E4%B9%A0%E9%A2%98)

## 1. 判断四种主体是否属于智能体

| 主体 | 判断及理由 | 类型 |
| --- | --- | --- |
| 高峰值算力的超级计算机 | 题设只给出了计算硬件和算力指标，无法从中建立任务目标、环境感知、自主决策和行动闭环。部署在其中的控制程序可以单独构成智能体。 | 按题设，超级计算机本身只是计算平台。 |
| 高速公路上的自动驾驶系统 | 系统持续获取道路、障碍物和自车状态，对安全距离等目标作出决策，经制动、转向等执行器影响环境，再感知车辆状态。 | 毫秒级避障属于反应层。若同时融合历史感知、追踪对象并规划轨迹，整车系统可描述为带内部环境模型的混合式智能体。 |
| 与人对弈的 AlphaGo | 智能体输入棋局和对手落子，搜索候选棋路，以胜局为目标评估局面并落子。落子产生下一状态，下一回合重新评估。 | 规划式智能体，价值网络和搜索提供以胜率为依据的评估。训练阶段通过棋谱和自我对弈学习策略，正式对局中的搜索与策略参数训练是两个过程。[Google DeepMind 对 AlphaGo 的技术介绍](https://deepmind.google/research/alphago/#our-approach) |
| 处理投诉的 ChatGPT 客服 | 按题设，完整系统能接收投诉、调用订单 API 取得事实、在权限内选择处理动作，并根据查询结果或用户反馈继续。客服可用的行动还包括解释进度和提交人工工单。 | 由 LLM 驱动，具备工具交互和多步规划。订单查询和工单权限来自应用系统的接口和授权。 |

分类先确定边界。同一个自动驾驶系统可以同时带有反应层和规划层，AlphaGo 的训练属性和对局时的决策方式也适合分别描述。[第一章 §1.1](https://github.com/datawhalechina/hello-agents/blob/main/docs/chapter1/%E7%AC%AC%E4%B8%80%E7%AB%A0%20%E5%88%9D%E8%AF%86%E6%99%BA%E8%83%BD%E4%BD%93.md#11-%E4%BB%80%E4%B9%88%E6%98%AF%E6%99%BA%E8%83%BD%E4%BD%93)

## 2. 智能健身教练的 PEAS

| 要素 | 设计 |
| --- | --- |
| P · 性能度量 | 记录计划完成率、动作纠正后改善率、提示延迟和用户反馈。按减脂、增肌或耐力目标分别统计趋势。单独评估风险提示是否及时、误报是否干扰训练，以及数据缺失时是否采用保守提示。 |
| E · 环境 | 用户的当前体能、训练目标和习惯，家庭或健身房的场地与器械，可穿戴设备及其连接状态，以及跨天的训练与恢复情况。 |
| A · 执行器 | 发送语音、屏幕或手表振动提示，提示调整姿势或暂停，调整计划中的强度、动作、组数和休息时间，生成训练复盘与一般饮食建议。 |
| S · 传感器 | 从可穿戴设备获取心率、活动强度和加速度，从可选摄像头获取姿态估计，从计时器获取训练与休息时长。通过用户输入获取目标、主观用力程度、不适和饮食记录。 |

- **部分可观察**。手表只测到部分生理量，摄像头可能被遮挡，疲劳和不适还需要用户报告。
- **随机**。睡眠、恢复和环境会改变同一训练计划的效果，设备数据也有噪声。
- **动态**。系统分析信息时，心率和动作仍在变化，实时纠正需要设置时延预算。
- **序贯**。增加当前一组的强度会影响下一组及后续恢复，动作决策会改变未来状态。
- **连续状态与离散动作并存**。心率、运动角度和时间连续变化，系统可在固定采样点选择维持强度、延长休息或提示暂停。

例如，心率信号突然断开时，教练可请求用户确认体感并降低下一组的计划强度。把「信号缺失」保留为独立状态，后续才能评估缺失数据时的应对表现。[第一章 §1.2](https://github.com/datawhalechina/hello-agents/blob/main/docs/chapter1/%E7%AC%AC%E4%B8%80%E7%AB%A0%20%E5%88%9D%E8%AF%86%E6%99%BA%E8%83%BD%E4%BD%93.md#12-%E6%99%BA%E8%83%BD%E4%BD%93%E7%9A%84%E6%9E%84%E6%88%90%E4%B8%8E%E8%BF%90%E8%A1%8C%E5%8E%9F%E7%90%86)

## 3. 电商退款用 Workflow 还是 Agent

| 方案 | 优点 | 代价和适用场景 |
| --- | --- | --- |
| A · Workflow | 有明确的路由和审批节点，处理一致，便于测试、审计和预计处理耗时。 | 规则变更要维护阈值和分支，用户描述模糊或凭证冲突时需要人工补充。适合商品类别、申请日期和金额都能确定的大量标准请求。 |
| B · Agent | 可以理解自然语言投诉，按需查询订单或物流，比较材料并追问缺失信息，适合情境多样的个案。 | 模型有时误读政策、转述错证据或给出不一致的判断，额外的模型和工具调用也会增加耗时。适合整理多来源材料、归纳争议点和协助处理边界案例。 |

**金额和日期的边界。** 按题意可将普通商品在时限内的金额区间定义成 `<100`、`[100, 500]`、`>500` 元。用整数分比较金额，分别测试 99.99、100.00、500.00、500.01 元。需求还须明确七天从哪个业务事件开始计算、第七天怎样判定、采用哪个时区，并用边界前后一秒验证。题设对特殊商品的拒绝规则与超期转人工规则都有描述，它们同时命中时的优先级应由政策负责人确定，待确认的组合可以进入人工审核。

**我的选择是方案 C。** 先用 Workflow 查询订单并执行硬约束。常规低金额请求按审核规则处理。证据不全、用户陈述与订单冲突或需要解释的请求交给 Agent。Agent 收集凭证、标注证据出处和不确定性、提出处理建议，高金额和规则冲突由相应人员审批。退款服务在实际出款前核验批准金额、订单、权限和剩余可退额，同时使用幂等标识避免重复退款。于是模型可以帮助缩短复杂工单的处理时间，关键操作则有明确的审批状态和记录。[第一章 §1.4](https://github.com/datawhalechina/hello-agents/blob/main/docs/chapter1/%E7%AC%AC%E4%B8%80%E7%AB%A0%20%E5%88%9D%E8%AF%86%E6%99%BA%E8%83%BD%E4%BD%93.md#14-%E6%99%BA%E8%83%BD%E4%BD%93%E5%BA%94%E7%94%A8%E7%9A%84%E5%8D%8F%E4%BD%9C%E6%A8%A1%E5%BC%8F)

## 4. 给旅行助手加入记忆、票务备选和反思

这是对第 1.3 节旅行助手的扩展设计。可以在已有的 Thought → Action → Observation 循环中加入三类状态。

| 功能 | 如何接入循环 |
| --- | --- |
| 记住用户偏好 | 以用户为单位保存经确认的偏好，例如兴趣为历史文化、单人预算 150 元。会话开始时加载与本次旅行有关的字段。当前请求新增的临时约束优先用于本次筛选，用户确认长期变更后再修改持久记录。 |
| 售罄时给备选 | 搜索候选景点后按旅行日期执行票务查询，返回可售、售罄或未知三种状态及查询时间。售罄的景点加入本轮排除集合，继续搜索满足天气、预算和距离条件的候选。票态未知时在建议中标明仍需确认。 |
| 连续三次被拒后反思 | 按会话记录连续拒绝次数、已推荐景点和用户明确表达的原因。第三次拒绝触发反思，汇总共同原因，修改排序条件或向用户询问最关键的未确认偏好。用户接受推荐或开启新任务时重置计数。 |

例如，用户三次都说「离住处太远」，反思后应把交通时间纳入排序，或先追问用户能接受的单程时长。若用户未说明拒绝原因，系统可以询问最想调整的一项条件，避免用猜测修改长期偏好。

```text
在会话开始时加载已确认偏好
把天气、候选和票态查询结果追加为 Observation
遇到售罄时排除当前景点并尝试其他候选
收到拒绝时记录该景点及用户给出的原因
累计三个连续拒绝时汇总原因并调整策略或请求澄清
找到符合硬约束且已确认票态的候选时给出推荐
达到查询或重试预算时说明已核实的信息和待确认项
```

可在实现后用固定工具返回验证四个情形。偏好跨会话按用户生效，首选售罄时给出符合约束的备选，票态接口超时时如实标明未知，三次拒绝后下一轮体现用户反馈。这里列出的是拟验收用例。[第一章 §1.3](https://github.com/datawhalechina/hello-agents/blob/main/docs/chapter1/%E7%AC%AC%E4%B8%80%E7%AB%A0%20%E5%88%9D%E8%AF%86%E6%99%BA%E8%83%BD%E4%BD%93.md#13-%E5%8A%A8%E6%89%8B%E4%BD%93%E9%AA%8C5-%E5%88%86%E9%92%9F%E5%AE%9E%E7%8E%B0%E7%AC%AC%E4%B8%80%E4%B8%AA%E6%99%BA%E8%83%BD%E4%BD%93)

## 5. 机械臂抓取仿真中的系统 1 和系统 2

场景设为数字孪生仿真。机械臂需要从桌面抓起一个指定工件并放入托盘。相机有视角遮挡，场景中还有其他工件。

- **系统 1 做快速感知。** 使用视觉模型估计目标类别、位姿、候选抓取姿态和置信度。用高频的状态反馈跟踪工件是否位移、抓取后是否滑落。
- **系统 2 做约束检查和规划。** 用仿真几何和关节约束验证候选抓取姿态，检查路径碰撞，选择一个可行轨迹，并在接近、抓取、抬升、放置各阶段核对条件。
- **协作从结构化观察开始。** 系统 1 把候选位姿、置信度和传感器时间戳交给系统 2。系统 2 可接受候选并规划，也可要求改变观察视角。仿真执行反馈和新传感器数据进入下一轮。

一个可复现的验证设计是在相同初始场景中先执行无遮挡抓取，再增加遮挡。如果感知置信度低，预期先换视角。如果目标识别正确但首选路径与旁边的工件相交，预期改选可行轨迹或停止。可记录无碰撞完成率、重规划次数和轨迹生成耗时。这里的双系统是对感知与规划分工的类比，测试为拟议方案。[第一章 §1.1.3](https://github.com/datawhalechina/hello-agents/blob/main/docs/chapter1/%E7%AC%AC%E4%B8%80%E7%AB%A0%20%E5%88%9D%E8%AF%86%E6%99%BA%E8%83%BD%E4%BD%93.md#113-%E6%99%BA%E8%83%BD%E4%BD%93%E7%9A%84%E7%B1%BB%E5%9E%8B)

## 6. 幻觉、循环上限和智能体评估

### 为什么会出现幻觉

模型擅长生成符合语境的文本，生成过程本身没有逐条核实外部事实。上下文缺失、训练知识过时、检索结果不相关或者工具返回自相矛盾时，模型可能自行补全。智能体还会把每轮输出加入后续上下文，一次错误判断可能继续影响搜索词、工具参数和最终结论。

以旅行助手为例，天气 API 返回的观测和景点搜索摘要里的天气描述可能不同。程序应保留来源和时间，回答当前天气时引用天气工具的有效结果。票态或温度拿不到时应表明缺失，并按预设策略重试或请用户确认。

### 取消五轮上限会有什么风险

工具超时、模型不断返回无效格式、重复查询相同参数或一直找不到合适结果，都可能让循环不退出。即使每轮可以单独完成，累积的请求仍会增加响应时间、API 费用、上下文长度和服务限流风险。一套终止条件可以组合步数、墙钟时间、累计工具调用和连续无进展阈值，触发后返回可核实的部分结果和失败原因。

### 怎样评估

| 维度 | 示例指标或测试 |
| --- | --- |
| 结果 | 任务完成率、用户要求满足率、结论与有效工具证据的一致率。旅行助手应正确转述温度，并给出适合该天气的景点。 |
| 工具使用 | 工具选择正确率、参数正确率、重复调用率。检查景点搜索是否收到上一轮的天气，是否查询了正确城市。 |
| 鲁棒性 | 在错误 Action、天气 API 超时、票态未知和搜索摘要与天气矛盾时，记录恢复率、正确降级率和终止率。 |
| 效率 | 统计每个任务的模型与工具调用次数、运行时间及 P95 延迟，以及实际使用费用。 |
| 安全与体验 | 统计越权操作率、错误完成率和用户满意度，检查系统在信息不足时能否说明不确定性。 |

准确率只度量选定口径下的正确比例。可以用同一批普通案例、边界案例和失败注入案例，对比智能体和「查天气 → 查景点 → 输出」的固定 Workflow，同时查看完成率、证据一致性、费用及延迟，判断额外决策能力是否改善了目标任务。[第一章习题与小结](https://github.com/datawhalechina/hello-agents/blob/main/docs/chapter1/%E7%AC%AC%E4%B8%80%E7%AB%A0%20%E5%88%9D%E8%AF%86%E6%99%BA%E8%83%BD%E4%BD%93.md#15-%E6%9C%AC%E7%AB%A0%E5%B0%8F%E7%BB%93)
