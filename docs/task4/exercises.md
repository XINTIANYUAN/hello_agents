## 1. 三种范式及智能家居架构

| 范式 | 如何组织决策与行动 | 适用特点 |
| --- | --- | --- |
| ReAct | 每次依据目标与已有观察选择下一动作，执行工具后将结果带回，继续决策。 | 状态变化或信息不足时，可以边查边调整。 |
| Plan-and-Solve | 先分解任务并安排依赖，再根据步骤和前序结果逐步求解。 | 问题结构较清楚时，计划便于检查遗漏与追踪进度。 |
| Reflection | 在初稿或执行结果上收集反馈，提出可操作的改进，再生成下一版本。 | 结果能够被评估，并且有额外调用预算时，适合迭代提高质量。 |

[ReAct 原论文][react-paper] · [Plan-and-Solve 原论文][ps-paper] · [Reflexion 原论文][reflexion-paper]

**智能家居以 ReAct 为基础。** 灯光、空调和窗帘需要查询真实状态，用户也可能在执行过程中修改要求。可以先读取设备状态和用户授权的场景偏好，选择一项动作，核对设备反馈，再进行后续动作。设备离线、温度传感器缺数或命令执行超时时，观察结果会改变下一步决策。设备状态和控制接口由应用维护，模型只选择已登记动作。

**组合方式。** 对「准备观影」这类场景，先规划灯光、窗帘和空调的目标状态。每一项由 ReAct 完成状态查询、控制与确认，失败时更新对应步骤。场景结束后，用 Reflection 比较目标状态、实际反馈和用户纠正，把经用户确认的偏好用于后续场景。即时手动控制优先进入当前执行状态，反思则可以在场景结束后运行。这套设计也适合有明确阶段、局部状态又会变化的旅行安排和设备巡检。[第四章 §4.2—§4.4][chapter]

## 2. 从正则解析到结构化动作

**当前实现的脆弱性。** 课程中的 `_parse_output` 从 `Action:` 匹配到回复结尾，动作解析又用带贪婪匹配的方括号模式。多组 Action、附加说明、嵌套方括号和文本里出现相同标签时，都可能让提取结果偏离预期。完成动作的正则与其他解析设置也有差别，多行答案或缺失结束括号可能触发解析失败。语法匹配得到工具名和字符串后，还要检查工具是否注册以及输入是否适用。[第四章 §4.2.3][react-code]

**结构化格式。** 可以让模型输出一个完整 JSON 对象，定义动作类型、工具名、参数或最终答案。先解析完整对象，再验证必需字段、字段类型、允许的键及动作分支。解析时检测重复键，执行时再次核对工具名、参数和权限。支持工具调用或受约束输出的模型接口也可以承担格式约束，应用继续执行相同的业务校验。[JSON Schema 对象约束][json-schema] · [Python JSON 解码规则][json]

本次在 [ReAct.py](../../code/chapter4/ReAct.py) 增加 `--format json`。动作对象恰好包含三个非空字符串字段 `thought`、`action`、`input`，分别表示简短行动说明、工具名或 Finish、字符串输入。解析器会拒绝重复键、缺字段和额外字段，执行器再核对实际工具。可用对象例如 `{"thought":"核对计算结果","action":"Calculator","input":"(123+456)*789/12"}`。

| 方案 | 优点 | 代价与边界 |
| --- | --- | --- |
| 文字标签加正则 | 实现短，观察 Action 文本较直观。 | 标签、括号和额外文字会增加歧义，类型与语义检查仍需编写。 |
| JSON 加字段校验 | 字段边界、类型和动作分支清晰，可以给出具体纠错反馈。 | 模型可能输出围栏、缺字段或错误类型，需要拒绝无效对象并有界重试。 |
| 接口工具调用与参数约束 | 由接口显式表达工具和参数，更易与执行器集成。 | 取决于服务和模型支持，工具结果与操作授权仍由应用负责。 |

固定输入对照每种格式各有 10 个用例，覆盖有效调用、完成动作的语法、多行排版、多行工具参数、缺字段、重复字段、尾随动作、尾随说明、未知工具和空参数。按最终可分派状态是否符合预期计算，文字格式为 9/10，JSON 为 10/10。文字格式会接受重复的 Thought，未知工具则由分派阶段拒绝。这个对照检验的是预设输入，完成动作的语法用例也单独标明，完整运行还会要求先有成功工具观察。[固定输入与逐例结果](experiments.json)

## 3. 计算器、调用纠错和工具检索

### 计算器应完成什么

计算器接收受支持的四则运算表达式，返回计算结果。题目中的表达式可统一为 `(123 + 456) * 789 / 12`，按顺序计算为 `579 * 789 / 12 = 456831 / 12 = 38069.25`。

实现时可以用 `ast.parse` 取得表达式结构，只接受数值、括号、一元正负及列入白名单的算术运算，再由执行器逐节点计算。为输入长度、节点数量和数值范围设限，除零或非法节点返回明确错误。该结构也方便添加受控的数学能力。[Python AST 文档][ast]

本次 [tools.py](../../code/chapter4/tools.py) 已注册 Calculator，采用上述 AST 白名单并限制表达式和中间值。实际模型调用该工具得到 `Observation: 38069.25`，随后输出 Finish。调用及结果保存在实验记录中，检查时同时比较工具值和最终数值。[真实计算器调用](experiments.json)

### 多次选错工具或参数时怎样纠正

把失败作为结构化 Observation 返回，内容包含错误种类、字段位置、允许的工具和参数示例。下一轮引导模型根据已确认的目标修正一个动作，保留失败记录。执行器累计连续失败次数，同样的无效调用不能反复执行。达到重试预算后返回已确认的部分结果，并说明缺少什么信息。工具恢复成功后，再按该任务的策略重置或保留计数。

处理未知工具、参数类型错误、计算表达式错误和真实网络故障时，反馈需要指出各自原因。例如，未知工具应提供可用工具名，除零则需要修改表达式或确认原题，服务超时可以按工具约定重试。对会更改外部状态的工具，重试还应查询请求状态并使用幂等标识。

已实现的 ReAct 循环累计连续失败次数，两次失败后追加具体纠错说明，并受最大轮次约束。验证时明确注入两条错误响应，第一条缺少 input，第二条使用未登记工具 UnknownCalculator。两次都被拒绝后，真实模型在第 3 轮选择 Calculator，取得 38069.25，第 4 轮 Finish。前两轮属于人工故障注入，后两轮调用本机 `qwen3.5:4b`。[故障输入、来源标记与恢复轨迹](experiments.json)

### 工具增加到 50—100 个时

为工具维护结构化目录，记录名称、适用条件、参数定义、示例、权限和副作用。先按用户授权和任务类型筛选，再用关键词或向量检索选出少量候选，把当前需要的完整参数说明给模型。一个大工具目录可以分成设备、订单、计算和搜索等域，域内再选工具。需要通过测试集测量工具检索召回率、选择正确率、参数错误率、延迟和 token 开销，避免候选筛选遗漏真正需要的工具。[第四章的工具执行器设计][tools]

## 4. 动态重规划、商务旅行与分层规划

**动态重规划。** 给计划步骤增加编号、前置依赖、目标、完成判据和状态。执行后记录输出及时间，判据不满足时返回失败原因。规划器读取用户约束、已完成步骤和失败证据，生成新版本计划。保留仍有效的结果，重新计算受影响的依赖，重新查询过期状态。对已发生的预订或支付，先取得真实状态，再按授权执行取消、修改或其他补偿动作，并限制重规划次数。[第四章 §4.3][plan]

例如，机票已确认而酒店没有房间时，新计划可以保留机票确认信息，替换酒店搜索条件，并重新核对酒店位置与取车时间。若用户的到达时限无法满足，应把可选调整及其影响返回用户。

**北京到上海的商务旅行。** 我选择高层 Plan-and-Solve 配合局部 ReAct。高层先固定会议时间、预算、出发到达约束及机酒车依赖。机票价格、房间和租车库存会变化，局部执行需要边查询边决策，取得每项确认后更新计划。仅做静态计划容易继续使用失效的库存，完全逐步探索则可能遗漏住宿、交通和预算之间的整体约束。

**分层规划。** 高层安排交通、住宿、市内出行与行程核对。交通子计划负责比较航班、核查时刻、确认报价和预订状态。住宿子计划负责日期、地点、预算和库存。各层输出可验证的状态，再由上层检查衔接。分层能缩小每轮决策范围、复用子计划并隔离局部失败，层间仍需统一日期、费用单位、依赖和最终完成标准。[Plan-and-Solve 原论文][ps-paper]

## 5. Reflection 的模型分工、终止与论文写作

**两个不同模型的影响。** 执行模型可以优先满足速度和成本，反思模型负责更复杂的错误检查及改进建议。候选模型应在同一任务集上测试初稿质量、修订接受率、修订后的正确性和总费用。强评审若给出执行模型难以实现的建议，可能增加失败轮次。可以把建议拆成明确修改项，附上失败用例或证据，并在必要时让能力更强的模型承担修订。角色分工会带来额外调用和串行延迟。[第四章 §4.4.5][reflection-cost]

**改进终止条件。** 原实现检查反馈是否包含「无需改进」，「尚不能认为无需改进」也会命中。可以用结构化评审结果表达通过项、阻塞问题和修改建议，减少从长段落里搜索词句的歧义。代码任务先检查语法、行为和边界用例，再比较事先定义的性能或质量指标。满足验收条件时结束，连续多轮没有有效改进时保留当前最优版本，达到时间、费用或迭代预算时说明未解决项。新版退步时可恢复上一份已验证结果。模型评审和外部验证共同提供依据。[第四章 §4.4.3][reflection-code]

**论文写作的多维反思设计。**

| 维度 | 检查什么 | 怎样改进和验证 |
| --- | --- | --- |
| 段落逻辑 | 主张、证据和结论是否衔接，概念前后是否一致。 | 列出跳步和冲突位置，调整论证顺序后回看上下文。 |
| 方法与创新 | 研究问题、相关工作和方法差异是否清楚，创新主张有无证据。 | 对照作者提供的材料和可检索文献，写明已证实的贡献及待补证部分。 |
| 实验与数值 | 指标、数据集、基线和实验条件是否对应，表格与正文是否一致。 | 从原始实验记录核对数值和单位，缺少实验时形成待办项。 |
| 语言表达 | 句意是否准确，术语、符号和缩写是否统一。 | 修改长句和含糊表达，检查修改是否改变原意。 |
| 引用规范 | 引用条目是否存在，出处能否支持对应主张，格式是否一致。 | 核对题名、作者、版本与具体证据位置，再生成引用格式。 |

每个评审维度输出「位置、问题、证据、建议、验收条件」。协调器先处理事实与证据，再处理结构和语言，逐轮保留版本差异与作者决策。评审发现需要新实验或缺失引用时，将其交给作者补充，后续修订只使用已取得的证据。这是论文写作助手的设计方案。[Reflexion 原论文][reflexion-paper]

## 6. 提示词结构、角色和 Few-shot

### ReAct 与 Plan-and-Solve 的提示差异

ReAct 提示给出工具目录、动作协议、当前问题和累计的 Action/Observation，要求每轮产生下一动作。这种结构让新观察进入下一轮决策。Plan-and-Solve 先用规划提示产生有顺序的步骤，再用执行提示提供原问题、完整计划、已完成结果和当前步骤，要求聚焦当前子任务。两者的差异体现在决策时机与上下文内容上。格式都需要程序校验，计划还要检查依赖和可执行性。[ReAct 提示与编码][react-code] · [规划提示与执行器][plan]

### 改变评审角色

本次为两个角色提供同一份固定的试除法初稿，使用同一个 `qwen3.5:4b` 和 `temperature=0`。效率评审的指令侧重复杂度，可读性维护者侧重命名、文档、边界处理和维护成本。这样可以比较从相同代码开始的实际反馈与修订。

| 角色 | 本次观察 | 调用与验证 |
| --- | --- | --- |
| 效率评审 | 建议改为埃拉托斯特尼筛法，修订版使用筛表。首轮反馈错误地把试除与筛法的复杂度描述成由 O(n log log n) 改到 O(n)。 | 3 次真实模型调用，最终通过 8 个参考输入，约 2.333 秒。 |
| 可读性维护者 | 同样建议筛法，并补充边界说明。修订文档写明 n < 2 的处理，循环变量使用 multiple。 | 3 次真实模型调用，最终通过相同 8 个参考输入，约 3.796 秒。 |

标准筛法的时间复杂度为 O(n log log n)。效率评审第二轮正确写出了这个复杂度，首轮反馈仍显示评审内容本身需要核对。两种角色在本次都选择了筛法，角色的预期侧重与实际输出只有部分对应。8 个输入的行为验证检验正确性，性能改善还需要在相同规模和环境中计时。[两种角色的原始反馈、代码和验证](experiments.json) · [课程筛法分析][reflection-code]

### 加入 Few-shot

为选定的动作格式提供完整示例，有助于说明工具调用、有效观察后的完成和错误后的修正。扩展示例集时，可以按这几种情形分别构造示例，保留相同待测任务、工具目录和解码参数，比较格式通过率、工具选择、参数准确性、纠错次数与 token。示例自身需通过执行器规则，并与待测问题分离。

本次基础提示中已有一个 JSON 格式样例，附加的完整轨迹示例展示 `2+3` 的 Calculator 动作、`Observation: 5` 和 Finish。待测题使用 `(123+456)*789/12`。基础格式样例和附加完整轨迹两组都用 2 次真实模型调用完成 Calculator → Finish，并输出 38069.25。两组墙钟时间分别约 0.720 秒和 0.640 秒。本次单题得到相同成功结果，稳定性与格式收益还需要更大样本检验。[示例对照代码](../../code/chapter4/Experiments.py) · [实际结果](experiments.json)

## 7. 电商客服智能体的产品设计

### 核心架构

我选择 Plan-and-Solve 管理退款工单的阶段，ReAct 获取订单、物流和政策证据，Reflection 审核存在争议的决策与回复。工单状态依次覆盖信息收集、政策判断、审批、退款执行、回复发送和结果确认。政策冲突、缺少关键材料或校准后的低置信信号触发复核。需要人工决策的工单进入人工队列，执行器根据审批状态和权限放行操作。

模型自报的信心可作为参考。是否需要复核还应检查政策命中情况、证据完整性、工具错误和已验证样本上的错误分布。阈值通过保留集及试点结果设定，同时观察误拒、误批和转人工率。

### 所需工具

| 工具 | 功能和返回信息 |
| --- | --- |
| 查询订单 | 按已认证用户及订单 ID 查询购买时间、金额、商品、已退款额和订单状态。 |
| 查询物流 | 返回运单、签收或运输状态及最近更新时间。 |
| 检索政策 | 查询对应政策版本、适用条款、限制和有效日期，并保留出处。 |
| 提交审批或人工工单 | 保存争议点、证据和建议，返回审批状态与处理编号。 |
| 执行退款 | 在批准金额与权限范围内执行退款，返回请求 ID、金额和处理状态，使用幂等标识处理重试。 |
| 发送邮件 | 根据已核验的业务结果生成并发送回复，核对收件人归属，返回发送请求 ID 与状态。 |

### 提示词设计

```text
请根据订单、物流和有效政策处理当前退款工单。
先核对证据，再给出适用条款、建议金额及缺失信息。
遇到证据冲突、政策歧义或权限不足时，提交复核并说明原因。
面向用户的回复应说明已核实的情况、处理进度和下一步。
金额、退款状态与预计进度采用工具确认的结果。
语气尊重、具体，使用用户能够理解的表达。
每项外部操作都经执行器校验当前审批状态和参数。
```

### 上线风险和应对

| 风险 | 技术措施 |
| --- | --- |
| 订单混淆或越权查询 | 将身份和订单归属校验放在工具服务，限制模型可访问的数据字段。 |
| 政策过期或推断失真 | 版本化政策，记录条款出处，使用明确的业务规则和独立用例验证决策。 |
| 用户材料或检索内容夹带指令 | 把材料标为待分析数据，工具选择与权限由执行器校验，持续测试指令干扰案例。 |
| 重复退款、部分失败或状态延迟 | 工单状态机、请求幂等、结果查询和对账共同维护一致性，状态未知时先核查。 |
| 错误邮件或重复发送 | 以已确认的退款结果生成回复，校验收件人与工单关系，保存发送状态和去重标识。 |
| 误批、误拒和反思循环过长 | 用保留集和试点监测决策质量、恢复率、人工接管率、耗时及费用，设置调用与迭代预算。 |

这是面向题设业务的架构与验证方案，规则、审批边界和时效承诺应在实际产品需求中明确。[第四章三种范式][chapter]
